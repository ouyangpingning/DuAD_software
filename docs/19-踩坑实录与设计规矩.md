## 一、"点了没反应"类

### 1. 测试绝不能写用户的真实 QSettings

`StageBridge` 默认用 `QSettings("DuAD","DuADSoftware")` —— 和真实程序**同一个作用域**。
早期 `tests/` 直接 `StageBridge()`，一跑就把假板子的 `host=127.0.0.1 / port=<随机> / token=deadbeef`
写进用户真实配置。后果：用户打开「平台控制」页，那三个框里是假板子的值，点连接当然连不上，
而失败提示很小 → 用户原话是**"点了没反应"**。

修法：`StageBridge(settings=...)` 支持注入，**所有测试都传一个文件隔离的 QSettings**：
```python
sfile = Path(tempfile.mkdtemp()) / "s.ini"
bridge = StageBridge(settings=QSettings(str(sfile), QSettings.Format.IniFormat))
```
新增任何会写 QSettings 的桥/测试时，照这个来。

### 2. "点了没反应"必须在设计上消灭掉

这是本项目反复出现的一类反馈（`LightControllerCard` 时代就有）。三条规矩：

- **点不动的按钮/卡片，必须在点击前就把原因写在旁边**。现在的做法：`StagePage` 在
  未配置时显示一条红色提示条「还没配置板子地址 —— 展开下面的「平台设置」填入」，
  而不是等用户点了才报错。
- **点击被拒绝时要给强反馈**：`StageBridge.connectDevice` 返回 `False` 时，页面
  **自动展开「平台设置」**，让用户立刻看到该填什么（原来只是卡片下面一行 12px 小字）。
- **取"输入框里的当前值"，不要取"已保存的值"**：`StagePage` 点卡片连接时用
  `setupPanel.fieldHost/fieldToken`（输入框内容）而不是 `setupPanel.host`（bridge 里已保存的旧值）。
  否则"改了 IP 但没点应用设置就点连接"会连旧地址，又是一次"改了没用"。

### 3. 建连必须有超时

`QTcpSocket.connectToHost` 连**不存在**的 IP 时，Qt 自己不超时，socket 会一直挂在
`ConnectingState` —— 卡片永远转"正在连接…"、永不报错。`StageBridge` 已加
`CONNECT_TIMEOUT_MS = 8000`，超时后给出可操作的三条排查（同一热点？IP 变了？客户端隔离？）。
`ZStageBridge` 同样有（两个桥各自独立超时）。

### 24. 触发器与它触发的面板不在同一屏时，光"展开"是不够的

2026-09-27 用户手绘重排「平台控制」页（两台板子各占一列）时暴露的一类毛病：
齿轮按钮画在**页顶的连接卡片**上，而它要展开的设置面板在**下面某一列里**。
只把 `expanded` 置真、不滚动，用户看到的就是"点了没反应" —— 这正是第 3 条那个
病的另一个形态（以前是"面板在页面最底下，展开后要滚半屏"）。

约定：**点触发器 = 展开 + 把容器滚到那个面板**（`StagePage._reveal` / `_openFold`）。
两个实现细节值得照抄：

- 滚动的锚点选**折叠头**而不是面板本身：折叠头的 y 不随展开/收起变化，
  而面板展开后的高度要等布局算完才知道（`Qt.callLater` 都未必赶得上）。
- 程序化滚动才加动画（`Behavior on contentY { enabled: 一个标志位 }`）。
  给用户滚轮/拖拽也套上动画，动画会和手指打架。

回归守卫：`test_stage_page.py` 11c4 点齿轮后断言 `contentY` 真的变了 ——
只断言 `_setupExpanded == True` 是**假断言**（那正是坏掉时也为真的那一半）。

### 10. 串行通道上的"慢命令"必须非阻塞 —— 否则急停是假的

2026-09-13 真机：**"台面撞到边缘不停，我在界面上按停止没反应。"**
根因是两层叠在一起（详见 `docs/17` §11）：

1. **板子的 TCP 任务是串行的**，阻塞版 `home` 要等到回零结束（几十秒）才回话 →
   我们发的 `stop all` 就排在它后面，界面上按了跟没按一样。
2. **电源被限流到 400mA**，顶住时驱动器欠压，回零**永远结束不了** →
   那条阻塞的 `home` 也就永远不返回。

规矩（对任何"可能很久"的命令都成立）：
- **客户端一律走非阻塞变体**（`move` 而不是 `g0`，`home … nowait` 而不是 `home`），
  结束状态由 `json` 的 `last` / `homing` 字段轮询判定。
- **急停命令永远排在最前面**（`_enqueue(..., front=True)`），并且**绝不能被禁用** ——
  它的 `enabled` 只跟 `connected` 走，不要跟 `moving`/`homing` 走。
- **界面上必须有一个按得动的退出方式**：回零中「自动回零」禁用，但要出现「中断回零」；
  回归守卫是 `tests/test_stage_page.py` 的 11c4。
- **报障"点了没反应"时，先问"这条命令会不会把通道占住"**，再问业务逻辑。
  只修其中一层，现象会原样复现。

### 12. 「连接」不是一个无害动作 —— 连接序列里不许有会动对端的命令

2026-09-13 真机：**"这个自动回零会在上位机点击连接的时候回零，其他情况不会回零。"**

排查方法值得当模板：把"连上之后到底发了什么"逐条列出来。
`_on_ready_read` 里只有 `travel` + 两条 `hset`（外加启动 `json` 轮询）；
`travel` 是纯固件闸、`json` 只读 → **唯一碰总线的是 `hset`（0x91）**，
而这台 PD42S1 **收到 0x91 就会自己开始找零点**（手册没写，实测如此）。

**规矩**：
- 连接时只允许发**幂等且无副作用**的命令。`hset` 这种"写进对端就会引发动作"的，
  一律换成只在本侧/固件侧生效的变体（这里是新增的固件命令 **`hcfg`**：只写板子 RAM）。
- 回归守卫：`tests/test_stage_bridge.py` **14f4** —— 断言连接后的命令序列里
  没有任何 `hset/home/move/g0/turn/abs/zero`。**加连接期命令时必须过这一条。**
- 原注释写的是"因为固件的 hset 只存 RAM"——那是**本侧**的理由，
  但代价发生在**对端**。写这类注释时要问一句"对端收到它会不会动"。

### 15. `_enqueue()` **没有返回值** —— 别写 `if not self._enqueue(...)`

`stage_bridge.py` 的 `_enqueue()` 只负责"排队 + 泵出去"，**没有 return**，
所以 `if not self._enqueue(...)` 里的 `not None` **恒为真** —— 那个分支永远会走。

真机后果是**静默的**：退出回零点那次 `move` 发出去了，但代码立刻走"失败分支"断开连接，
于是**永远不回零点**，而且不报任何错。已改成直接调用 + 用"命令应答完 / moving 归 0"
两段等待来判断成功。`tests/test_stage_bridge.py` 第 16 组断言"退出时真的发了那条 move"，
专门钉这一类"发了就走"的错误。

**同类坑**：本项目其它"看起来会返回布尔"的内部方法（`_pump_queue`、`_apply_json`…）
也都没有返回值 —— 调用前先看一眼实现，别按名字猜。

### 16. 「位置读数是 0」**不能**证明"台面在零点"

驱动器上电时也是从 0 开始数的 —— 于是"随便停在哪儿"和"正好停在零点"读出来**一模一样**。
判断基准还能不能信，必须靠**固件的基准闸**（`json` 的 `datum`，在 RAM 里，板子一重启就清空）
当"电源有没有断过"的证人；位置只用来判断"我们不在的时候有没有人动过它"。
`_check_park()` 就是这两条一起看（见 `docs/17` §11.4）。

### 17. 能做"选项"的东西，先问一句"它会不会挪走整个坐标系"

`stage/home_corner`（回零目标角落，四选一）被删掉了（2026-09-13，用户拍板：
**"固定零点在 X 轴左侧和 Y 轴的外侧"**）。原因不是"少一个控件更清爽"，而是：

**零点同时被预设位置、工作区、退出回零点三处引用。** 一旦它可选，
就可能出现"这次回左·外、下次回右·里"—— 那不是换个角落，那是**把坐标系整体平移**，
而所有预设坐标会**静默地全部失效**（界面看起来一切正常，去的地方全错）。

→ 现在是一个常量 `DATUM_CORNER = (-1, -1)`，并在缩略图上画了个绿方块标出来，
图例写「零点（X 左 · Y 外）」—— 把"家在哪"画出来，比让人从下拉框里记更可靠。

**推广**：凡是"改了它会让已有数据失效"的设置，默认都应该是**不可选**的；
非要可选，就必须同时给它一个"已有预设已作废"的显式提示。

## 二、QML / 布局类

### 6. QML 绑定里**不要调函数** —— 它没有依赖追踪

```qml
diagText: StageBridge.diagText()      // ✗ 只在创建时求值一次，之后永远不刷新
diagText: StageBridge.diagText        // ✓ 带 notify 的 Property 才会跟着变
```

踩过的坑：`StageBridge.diagText` 原本是 `@Slot(result=str)`，QML 侧写成
`diagText: StageBridge.diagText()`，于是诊断面板的「板子状态」**永远显示"未连接"**，
哪怕板子早已连上并在 1Hz 轮询。这类 bug 不报错、不警告，纯粹是"数字/文字不动了"。

规矩：**凡是要跟着状态变的文本/数值，一律用 `Property(..., notify=...)`**，
需要计算就在 Python 里算好。同理，页面里拼提示语要在 QML 里用**属性表达式**
（如 `StagePage._gateHint` 读 `StageBridge.datum/travelSet/moving`），
不要调 `StageBridge.datumHint()` 这种函数。
回归测试：`test_stage_bridge.py` 的 14c 与 `test_stage_page.py` 的 11c2。

### 9. QML 里一个"撑爆宽度"的坑：坏的是 A 行，坏掉的是 B 行

真实案例（平台页诊断面板）：`ComboRow` 的下拉框和 `SwitchRow` 的开关**完全没画出来**，
只剩标签。量出来的几何是：

```
homeKind (ComboRow)    w=628   ← 但父 ColumnLayout 只有 412
homeRev  (SwitchRow)   w=628
boardStatus(ReadonlyRow) w=628 ← 元凶
    ComboBox 在 x=478、开关 Button 在 x=584 → 都在 412 之外，被卡片裁掉
```

根因：**「板子状态」那一行的长文本（70+ 字符）没有 `elide`/换行**，它的隐式宽度把整个
ColumnLayout 撑到 628；同一列里 `fillWidth` 的兄弟行跟着变成 628 宽，它们**右侧的控件**
就被推出了 460 宽的卡片。

规矩：**任何可能很长的 Text 都要能收缩**（`Layout.fillWidth: true` + `elide` 或 `wrapMode`），
否则它会连累同一列的其他行。已加固 `ReadonlyRow` / `ComboRow`（标签加上限）;
诊断摘要这种超长内容改为「标签 + 自动换行块」，不再用单行组件。
回归守卫：`tests/test_stage_page.py` 的 11c2b（断言行宽 ≤420 且子控件右边界在卡片内）。

### 14. QML 属性会自动生成 `<名字>Changed` 信号 —— 别撞名

`property int homeCorner` 已经自动生成了 `homeCornerChanged`。
再写 `signal homeCornerChanged(int)` 会让**整个页面**加载失败：
`Duplicate signal name: invalid override of property change signal or superclass signal`。
改名成 `homeCornerPicked` 即可。这类错误由 `tests/test_stage_page.py` 第 1 步
（页面加载）直接抓到，不用等运行时。

### 18. 删 UI 要给"反向断言"，否则删掉的东西会偷偷回来

2026-09-13 删掉整套无限位回零界面时，`test_stage_page.py` 的 11c2b 不是删掉了事，
而是改成**反向断言**：
```python
for gone in ("homeKind", "homeCorner", "homeButton", "homeAbortButton",
             "homePassXm", ... "applyHomeCfgButton", "homeRpm", "homeMa"):
    r.check("已删除的控件不在界面上：" + gone, find(gone) is None)
```
理由：这些控件每一个都对应过真机上的困惑（"点了没反应"/"回零期间按停止没反应"），
是**带着教训删掉的**。只写"现在还剩什么"的断言，下次有人合错分支就能把它们放回来而无人察觉。

### 22.1 Z 轴卡片踩出来的三条 QML 坑（2026-09-27）

1. **`Item` 的 `z` 是 FINAL 属性**：QML 里写 `property real z` 会让**整页加载失败**
   （`Cannot override FINAL property`）。Z 遥测要显示"高度"时改用 `posZ` 即可。
   （同一族还有 `x`/`y`/`width`/`height`/`enabled` 等 —— 组件里声明同名属性会得到
   `overrides a member of the base object` 警告，工程里既有的 `SliderRow`/`InputRow`
   /`SwitchRow` 就是这么来的，属已知噪音。）
2. **Repeater 的 delegate 不在 QObject 树里**（Qt 6.11 `QQmlDelegateModel`）：
   `findChild(QObject, "zStepChip_10")` **找不到**，必须遍历可视树 `QQuickItem.childItems()`。
   测试与几何守卫都按这条写。
3. **测试环境的 URL 解析语义必须与 main.py 对齐**：不设
   `QML_COMPAT_RESOLVE_URLS_ON_ASSIGNMENT=1` 时，`../images/Z轴平台.svg` 会被解析成
   `pages/images/…`（图标**静默消失**，没有任何报错），而真程序里是对的。
   平台页相关测试文件与 `render_page.py` 顶部都已对齐这个变量，并加了"图标能打开"的断言。

### 22.2 结构差异要写进注释，否则会被"修回去"

Z 卡片的 `ZStageJogPanel` **不直接用桥的 `canMove`**，而是从各自带 notify 的属性本地算。
原因：`canMove` 的输入里有一位是 `moving`，而桥乐观置位时最早只发了 `movingChanged`
—— QML 直绑 `canMove` 在"刚点完点动"那一刻不会重算，按钮看着还能点。
桥侧已修（`_note_motion_sent` 现在**同时**发 `telemetryChanged`），但面板仍保留本地计算，
理由写在面板注释里。**"桥已修好"不等于"这段本地计算是多余的"** —— 别顺手删。

### 23. 跨文件取控件属性：id 是不出文件的

2026-09-27 QA 探针实测到一条**既有 bug**：X/Y 的「应用设置」按钮点击后抛
`ReferenceError: xminRow is not defined` —— `StagePage.qml` 的 `onApplyRequested` 里
直接写了 `xminRow.text` / `rpmRow.sliderValue`，而那些 **id 属于 `StageSetupPanel.qml`**，
在页面里根本取不到。后果是后面三条下发（工作区/速度/连接）**一条都不执行**，
正是本项目最忌讳的"点了没反应"（而且异常只在点的那一刻出现，不点就永远发现不了）。

修法与约定：**子面板要暴露 `field*` 这类 readonly 属性**（值 = 输入框当前内容），
页面只用这些属性。`StageSetupPanel` 与 `ZStageSetupPanel` 现在都齐了。
新增跨文件取值时照这个来 —— **别再从页面里伸手去够子组件的 id**。

### 25. 响应式版面下，几何守卫要用**相对**判据

几何守卫原来写"卡片内容区每一行 ≤ 420px"（卡片恒为 460 时代的数）。
2026-09-27 页面改成两列、卡片宽度由窗口决定以后，满宽的正常行全被报成 FAIL。
**守卫一旦开始误报，下一个人就会顺手删掉它** —— 所以判据要写成相对量
（"行宽 ≤ 内容区宽"、"右边界 ≤ 卡片宽"），而不是某个写死的像素数。

配套的一条测量纪律：断言宽/窄形态前**先把窗口宽度设成你要的形态**。
offscreen 平台的屏幕只有 800×800，harness 里写的 `width: 1400` 在窗口创建时会被裁
（实测裁到 ~945），于是"宽屏两列并排"的断言全红，而人会以为是布局没生效。
排障手法：把 `page.property("width")` 打进断言消息里 —— 一眼看见前提是假的。

### 26. 界面只放"操作 + 当下状态"，静态说明进注释/文档/控制台

2026-09-28 用户对「平台控制」页的反馈是**"UI 内容上有点不是很美观"**，并给了方向：
"只把最常用的操作留在上位机上，细节或者测试留在后端控制台。"
量化之后病根很清楚：那一页贴着 **32 段 / 1050 字**的 10px 灰色说明文字（"为什么这么设计"），
加 9 张同色卡片、5~6 个红绿圆点状态条。用户天天用，这些字就只剩噪音。

定下的规矩：

| 类别 | 去哪 | 例子 |
|---|---|---|
| **当下状态** | 留在界面 | 连接卡的状态行（**只画异常项**，正常不占地方）、闸门原因（`gateHint`）、故障文本 |
| **该怎么做** | 留在界面 | "还没配置地址，点这里展开"、"预览起不来，去相机设置" |
| **动作** | 留在界面（短标签 + ToolTip） | `⏻ 失能` / `⌂ 设为原点` / `■ 停止` |
| **为什么这么设计** | 进代码注释 + `docs/` | "为什么要非阻塞"、"跳齿与转速的关系" |
| **一次性参数 / 排障细节** | 进板子控制台（或页面里协议框的自定义命令框） | 转速、软限位、上电回零、关节读数、方向符号、诊断日志 |

配套的三条硬约束（都有测试钉着）：

1. **首屏够得着**：点动方向键、急停、设为原点必须落在 1080p 首屏内
   （`test_stage_page.py` 12a2 量 `mapToItem` 后的底边 vs 列高）。
   这条是**真的会红**的：当时「停止」的底边落在折叠线以下 9px，是靠它发现的 ——
   修法不是"再挤一点"，而是删掉读数卡里三行重复信息 + 把十字键从 74px 收到 60px。
2. **不许长回来**：删掉的说明文字用"禁止短语"守卫（两个页面测试各一条），
   半年后有人再贴回去就会红（同第 18 条的精神）。
3. **删 UI 不等于删能力**：比如删掉「上电自动回零」开关时，桥的 `setAutohome()` 必须留着，
   反向断言钉的是**界面入口**（`find(...) is None`）+ **能力还在**（命令仍能下发）。

卡片数也顺手砍了一半：读数卡改成**无卡片**（`PositionReadout.flat` / `ZStageTelemetryPanel.flat`，
大号读数当"列头"），只留操作卡与折叠区 —— 一屏里同色圆角块从 9 张降到 3~4 张。

**两条版面硬规矩**（2026-09-28 用户第二次反馈后定的，都是"看着别扭"的具体形态）：

- **内容宽度（这条规矩换过方向，别拿旧版当依据）**：2026-09-28 上午用户先说"内容定宽
  （=页顶两张连接卡的宽度 812）、居中、两侧留空"；当天下午第二张手绘稿落地成三列后
  用户**改口：手绘稿本来就是按全屏画的，UI 要填满整页**（v4.0 按 884 定宽居中被否：
  "现在的 UI 非常窄"）。现行规矩（v4.1）：三列**自适应填满** —— 左右列 21% 页宽夹在
  [200,340]、中列吃满剩余；预览卡片占满中列（画面等比、允许黑边、高度上限 0.45×页高）；
  手动控制卡各半、封顶 480、居中。"填满"和"控件拉长"仍是两回事：填的是**列宽**，
  卡内控件照样不一律 fillWidth（见下一条）。
5. **嵌套布局（`RowLayout`/`ColumnLayout` 当子项）的 `Layout.alignment` 与
   `Layout.preferredWidth` 都不可靠**（2026-09-28 实测，Qt 6.11）：
   卡片行明明写了 `preferredWidth: 812 + AlignHCenter`，实际被拉到 **1640**、
   两个 `ColumnLayout` 各 801px、两侧弹簧只剩 1px；另一处 `AlignHCenter` 直接不生效（x=0）。
   **修法：外面套一层普通 `Item`**，让它承接 `Layout.*`，里面的布局用
   `width: parent.width` / `anchors.horizontalCenter` 跟随。
   ⚠ 两个连带坑：① 外层 Item 的 `implicitHeight` 要绑里面那个布局的 `implicitHeight`，
   所以**里面那个布局的 id 不能省**（省了 Item 高度直接变 0，整行消失）；
   ② 折叠状态要放在**外层 Item** 上 —— 里面那列即使 `visible: false`，
   它的 `implicitHeight` 仍会被算进外层高度（实测页面凭空长高 1600px）。
6. **控件不许一律 `fillWidth`**。动作按钮用
   `implicitWidth: implicitContentWidth + 留白`，行尾加一个
   `Item { Layout.fillWidth: true }` 当弹簧把它推到左边；
   该固定的固定（上下键 260 居中、输入框 132/176），表单卡片限宽 560 居中。
   用户原话："所有的组件的大小都是填满的，这样很不好看。"
   ⚠ 留白别贪大：Z 卡三个动作按钮并排时 +36/+44 就会超出内容区 12px
   （几何守卫 14 组当场抓到，收到 +26/+34 才合适）。

### 28. Qt 测试里"点一下"和"找控件"的三个坑（2026-09-28 连踩）

1. **Repeater 造出来的 delegate 不在 QObject 树里**：实测 `parent()` 是 **None**，
   `findChild`/`findChildren` 一个都找不到（`count` 却是对的、`childItems()` 里也有）。
   要按 objectName 找它们，必须走**可视树**递归 `childItems()`。
   （AGENTS 里"delegate 在 ListView 的 contentItem 里"是同一类问题的另一种表现。）
2. **`MouseArea.clicked` 在 Qt 6 带 `QQuickMouseEvent*` 参数**：`clicked.emit()` 直接
   报 `needs 1 argument(s), 0 given`。要模拟点击就用
   `QTest.mouseClick(win, Qt.LeftButton, Qt.NoModifier, QPoint(x, y))`。
3. **`QTest.mouseClick` 用的是窗口坐标**：控件在视口之外（比如展开的「高级」深处、
   y≈2000）时点击会落在窗口外面 —— **等于没点**，而且不报错。点之前必须先
   `contentY` 滚过去（或把窗口开高）。
   ⚠ 顺带一条 QML 侧的：`pageFlick.contentHeight` 在"刚把某个 `visible` 置真"的那一瞬间
   还是旧值 —— 想"展开后滚过去"必须**等一帧**（`Timer { interval: 60 }`），
   否则 `maxY=0`、滚不动（表现是"面板展开了但没滚过去"）。

### 29. 嵌套 RowLayout 的 implicitWidth 会成为"最小宽度"，把整列顶溢出（2026-09-28 三列版面）

`StagePage` 改三列版面（左右列 200 / 控制卡 224）后，Z 卡几何守卫红了：
`zJogBody`（ColumnLayout）宽度 192，但**所有** fillWidth 子行都是 198。

逐层定位（最小复现确认是 Qt Quick Layouts 的行为，不是我们的 bug）：

- ColumnLayout 的 `implicitWidth` = 最宽子项的隐式宽度；**当列的实际宽度 < implicitWidth
  时，fillWidth 子项按 implicitWidth 排、直接横向溢出**（不是按宽度截断）。
- 罪魁是**步长行**：嵌套 RowLayout（"步长" + 4 个 chip）的 implicitWidth ≈ 198
  —— 嵌套布局把自己的 implicitWidth 当作**最小宽度**上报，超过列宽就顶破。
- 普通 Text（fillWidth + `wrapMode: Text.Wrap`）**不会**引发这个问题（实测列隐式宽 274
  时子项仍按 192 排）—— 只有"收不小"的嵌套布局会。

**规矩**：往窄列里塞嵌套 RowLayout 时，把它的 implicitWidth **算出来**（子项隐宽 + 间距），
确保 ≤ 列宽。这次是步长行间距 6→4、chip 52→36（行隐宽 198→188 ≤ 192）。
回归守卫：`test_zstage_page.py` 第 14 组（量的是"每一行 ≤ 内容区宽"，这类溢出直接红）。

### 30. 多列版面的宽度要"三条约束一起夹"，否则两头都难看（2026-09-28 v4.2）

`StagePage` 从"两列/抽屉"改成**三列**（左右窄列 = 各自的连接卡+状态+设置，中列 = 预览+
两张控制卡+高级）之后，用户反馈"**现在的 3 列占据的空间上存在问题**"。
v4.1 的算法是"侧列 = 21% 页宽，夹在 [200, 340]"，全屏（页宽 1680）算出
**侧列 340 / 中列 976** —— 两个具体毛病：

1. **侧列太窄 → 连接卡副标题被裁**：`127.0.0.1:3333 · 24.2V · 已使能 · -58dBm`
   在 340 里放不下，右边被切掉（截图里是 `… · -58d`）。
2. **中列太宽 → 预览被拉成大黑框**：预览卡占满中列宽（976），而画面按 2448:2048 等比
   只占中间 **559px**，两侧各 ~200px 纯黑。整页最显眼的东西变成一块黑。

**规矩：侧列宽 = min(比例, 上限, 让中列保住下限的那个值)，再兜一个硬下限**：

```qml
_sideMax = 420; _midMin = 380
_effSide = max(160, min(_sideMax, 页宽 × 0.24, max(160, (页宽 − 2×间距 − _midMin) / 2)))
```

- 宽屏看**比例**（手绘稿 160:350:160 ≈ 24%:52%:24%）：1680 → 403/850、1280 → 307/642；
- 窄屏**先保中列**（中列里是操作卡，不能被挤没）：730（最小窗口）→ 163/380。
- **不要**为了"预览好看"去改预览的取景规则 —— 病根在多列配比，改配比就行。

配套一条（同一版的第二个坑）：**并排的卡片用 `GridLayout` + 动态 `columns`**。
v4.1 是 `RowLayout` + 两个弹簧 + `preferredWidth: min(半宽, 480)`：中列一窄，
卡片就被挤到比内容还窄（RowLayout 不会换行）；宽了又被 480 封顶、两侧留空。
改成 `GridLayout { columns: _jogSideBySide ? 2 : 1 }` + 单卡 `Layout.maximumWidth: 520`
+ `Layout.alignment: Qt.AlignHCenter` 之后，宽了并排、窄了自动上下叠、超宽屏封顶居中。

配套第二处：**连接卡副标题按列宽取舍**。`host:port · 24.2V · 已使能 · -58dBm` 在
340 宽的列里放不下（被 elide 成 `… 已使…`），而信号强度不是"能不能动"的判据 ——
`_effSide < 360` 时就不显示它（IP/电压/使能状态必须留着）。

回归守卫：`test_stage_page.py` / `test_zstage_page.py` 的几何守卫（每行 ≤ 内容区宽）
+ `tests/render_page.py` 在 1680/1280/900/730 各渲染一遍目检。

### 31. 页面里的滑块**不能劫持滚轮**（2026-09-28 用户真机反馈）

用户报的现象："**滚轮上下移动的时候会影响到滑条**"。这是 `SliderRow` 的 `onWheel`
默认**接受**了滚轮事件（MouseArea 的 onWheel 不显式放开就会吃掉），于是：

- 想滚页面时，鼠标扫过任何一个滑块 → **值被改**，页面还不滚（事件被吃）；
- 更糟的是 `commitTimer` 350ms 后会把新值**写进板子**（速度/软限位）——
  用户以为只是在滚页面，实际改了机器参数。

**规矩**：滚轮只在**带修饰键**时才归滑块（`Ctrl` 更细 / `Shift` 更粗，原有语义不变），
否则 `wheel.accepted = false` 让它冒泡给父级 Flickable：

```qml
onWheel: function(wheel) {
    if (!control.enabled) return
    if (!(wheel.modifiers & (Qt.ControlModifier | Qt.ShiftModifier))) {
        wheel.accepted = false      // 交给页面滚
        return
    }
    ...
}
```

同类判据：**任何"鼠标悬停就能改值/发命令"的控件，都要先问一句"用户是不是只想滚动页面"**。
（点动按钮是按下才发，天然没有这个问题。）

### 11. 测试替身必须复刻"慢"和"抢占"，否则给的是虚假安全感

于是第 10 条"阻塞 `home` 期间 stop 进不来"的缺陷**在测试里根本复现不出来**，

### 13. 界面表达不了的自由度 = 功能不存在

2026-09-13 用户报：**"现在回零只有左右回零，没法在角落里回零，也就是没有 Y 轴里外的回零。"**
固件一直支持任意方向组合，**但界面只给了一个「方向反转」开关（两轴共用）** ——
而 CoreXY 里"两轴同向 = 纯 X、两轴反向 = 纯 Y"，两轴永远同向就永远只能走一个方向。

改法：把"想要哪个角"当输入，**方向由固件按 `COREXY_DEFAULT` 反推**
（`home corner <xdir> <ydir>`）；界面只提供 4 个角落 + 4 个单趟调试按钮。
那个「方向反转」开关**删掉**了 —— 它在新流程里完全无效，留着就是"点了没反应"。

**规矩**：设计参数面板时先问"用户要描述的自由度，这几个控件够不够表达？"
表达不了的参数不是"用户不会用"，是**功能缺失**。

### 20. 异步插进来的协议行必须单独分流，不能算成"命令输出"

Z 轴的协议显示框要显示**驱动器层的原始报文**（固件 `trace on` 镜像回来的 `@T`/`@R` 行）。
这些行是在**总线事务内部**产生的，所以它们出现在一条命令的输出**中间**，不属于任何
一次请求-应答。`ZStageBridge._handle_line` 把它们放在**第一个分支**（`line.startswith("@")`）
直接丢进协议框，`_resp_lines` 一行都不收。

⚠ 如果偷懒让它们走普通分支：命令输出会多出几行无关内容，而"失败时显示最近 3 行"
（`_finish_command`）就会把帧报文当成拒绝原因显示出来 —— 排查方向直接被带偏。
`tests/test_zstage_bridge.py` 第 17 组断言 `←` 开头的行里**没有**帧行（反向断言）。

配套两条：行数必须封顶（`PROTO_CAP=400`，开着帧镜像时每秒上百行）；左右不能靠从机地址区分
（**两台驱动器地址都是 0x01**），要用 UART 端口。

### 21. 两块板子 = 两个桥；"共用一条连接"是另一个方案，别混

「平台控制」页管**两个平台**：X/Y（`StageBridge`）和 Z（`ZStageBridge`）。
它们是两台设备、两条 TCP，各自轮询、各自队列、各自错误状态。

⚠ 别为了"少一个连接按钮"把它们合并成一个桥：板子的 TCP 服务端是**单客户端**的
（第二个连接回 `#ERR busy`），合并就必须做"按前缀分流 + 一套共享的在途/队列状态"，
而那会把两块板子的故障域绑在一起 —— 一块掉线另一块跟着报错。收益为零。

### 27. 两块板子共用的东西：合并流 + 前缀，能力从桥上报

2026-09-28 用户要求"协议显示改成公用的"（"我只要将 usb 线接到不同的板子上，
这个就会有对应的指令"）。落地方式是 `Src/proto_log.py`（单路记录器）+ `Src/proto_hub.py`
（合并器），要点四条：

1. **合并 + 前缀，而不是"选一块看一块"**（`[XY] → json` / `[Z] ← #OK`）：
   两块板子可以同时连着，排障时最想看的恰恰是"谁先答的、谁没答"，分两个框就没法对齐时间线。
   界面上的来源选择器只决定**命令发给谁**与**帧镜像跟着谁**。
2. **封顶与节流分两层**：单路 `PROTO_CAP=400`，合并 `HUB_CAP=800`。
   `lineAdded` **逐行**发（给合并器 append，很便宜），`changed` 才节流（80ms）。
   ⚠ 节流的理由不是"好看"：一行一次 emit 会把 GUI 线程打满，GUI 一卡就不读 socket →
   固件 `send()` 阻塞到超时 → **反过来伤害固件**。
3. **暂停/清空两路一起**（`ProtoHub.setPaused/clear`）：用户按暂停是想"冻住这一刻"。
4. **能力（capability）从桥上报，绝不在界面里写死**：`trace`（驱动器帧镜像）只有 Z 轴那块
   板子的固件有 → `StageBridge.supportsTrace = False` / `ZStageBridge.supportsTrace = True`；
   界面据此把开关置灰并写明原因。**同一个事实只许有一份**（同第 19 条）——
   以后二轴固件补齐 `trace`，只改桥里那一个布尔值。

### 8. 布局问题"量"不要"猜" —— 有截图和几何两条路

### 32. **别拿"探针脚本里的表现"当结论** —— 我据此把一条规矩写错了（2026-09-28）

⚠ **本条是一次自我更正，请连着"当初为什么写错"一起看。**

美化「平台控制」页时想给卡片加阴影、给图标染色，写了几个最小探针脚本，得到：

| 用了什么 | 探针（孤立 `Window` + `processEvents`）里的表现 |
|---|---|
| `QtQuick.Effects.RectangularShadow` | 一个像素都不画，也不报错（连 `color:"#ff000000" blur:20 offset:(0,10)` 都空白） |
| `Qt5Compat.GraphicalEffects.ColorOverlay`（`IconImage.qml` 内部用的） | 同上，**整张图标不渲染**；而同一个 `Window` 里的普通 `Image` 画得出来 |

于是我写下"shader 特效在软件渲染下整个不画，所以 `render_page.py` 的截图里图标**从来是空的**"。

**这句是错的。** 后来把真实页面渲染出来一看，图标画得清清楚楚：
在 `final_stage.png` 里量十字键那个箭头，区域内有 226 个深色像素，
颜色正是 `Colors.textPlaceholder`（我设的禁用色）—— 说明 `ColorOverlay` 在页面里**正常工作**。
（"容器里 `QSG_RHI_BACKEND=opengl/vulkan` 会回落成 `Loading backend software`"这句是实测的；
但"软件后端 ⇒ 特效不画"是我**从探针外推的**，不成立。）

真正的教训不是"特效不能用"，而是：

- **探针脚本能证明"能"，很难证明"不能"。** 孤立 `Window` 里少一点上下文（尺寸？某次
  `update()`？渲染循环的第几帧？）就可能不画，而你会把"我的探针没搭对"读成"平台不支持"。
  要否定一件事，**得在真实使用场景里否定** —— 对本项目就是页面渲染
  （`tests/render_page.py` / `tests/render_pages.py`）。
- 真要目检**图标本身**（形状、粗细、四边留白），用 `tests/render_icons.py`：
  它用 `QSvgRenderer` 直接渲 SVG，不过 QML，最省事也最不受环境影响。

**所以实际留下的规矩只有两条（都仍然成立）：**

- 卡片"浮起"用 `pages/components/CardSurface.qml` 里**两块普通 Rectangle**
  （比卡片下移 2px 的圆角矩形当硬阴影）—— 不是因为特效画不出来，而是它
  **更简单、且已在页面里验证过**；按钮"按下去"同理（`ThemedButton`）。
- **图标路径的正确性仍然靠断言兜底**（第 22.1-3 条：路径错 → 静默消失，不报错）。
  `tests/test_stage_page.py` 12e 与 `tests/test_ui_theme.py` 会把每个 `IconImage` 的
  `source` 解析成文件路径查存在。
  ⚠ 读 `property("source")` 拿到的是 **QUrl 对象**，`str(u)` 出来是
  `PySide6.QtCore.QUrl('…')` 这种 repr，必须 `u.toString()`，否则守卫自己会"全部不存在"地误报。

### 33. 没写 `background` 的 `Button` 用的是 **Fusion 默认样式**，它不吃 `Colors`（2026-09-28）

「平台控制」页美化后用户截了张图，指着「移动到该位置」问
"可以将这个页面中的按钮设置成可以随主题变化吗"。根因是那 4 个按钮
（移动到该位置 ×2、应用设置 ×2）**根本没写 `background`** ——
Qt Quick Controls 会用当前 style（本项目强制 Fusion）的默认外观：
灰底 + 深灰渐变，和 `Colors` 一点关系都没有。于是：

- 在一片白卡片里像从别的软件剪下来贴上去的；
- 切暗色主题 / 换配色时**纹丝不动**（别的控件都在渐变，就它不变）。

规矩：**这一页所有按钮一律走 `pages/components/ThemedButton.qml`**
（`tone: neutral | soft | danger | dangerSoft`），颜色只来自 `Colors`。
新写按钮时若发现 `background` 没写、或自己又抄了一遍 `Rectangle`，就是错的。

⚠ 同一类坑还有两个变体，都真踩过：
- `Colors` 单例里**没有** `transparent`。写 `Colors.transparent` 得到 undefined，
  运行时只报一行 `Unable to assign [undefined] to QColor`，界面看着正常但颜色是错的。
  透明一律用字面量 `"transparent"`。
- **禁用态别用压透明度**（`opacity: 0.35`）：实心图标会淡成一片浅影，
  用户真机截图里把十字键的箭头看成了"这个图标是不是没有修改"。
  禁用应该**换颜色**（`Colors.textPlaceholder`），形状始终清楚。

### 34. 测 `visible` 之前要先展开折叠节 —— Qt Quick 的 `visible` 会**向下传染**（2026-09-29）

给限位电流加"甜点区警告"时写了这样一条断言：填 120mA → `warn.property("visible")`
应为 True。结果它稳定失败，而 `warn.property("text")` 明明是那句"低于 300 mA…" ——
同一个对象、同一次求值，文本说"该显示"，可见性说"没显示"。

根因：`Item.visible` 在 Qt Quick 里是**向下传染**的（父项 `visible: false` ⇒
子项读出来的 `visible` 也是 false），而那个警告住在
`StagePage.qml` 的 `FoldBody`（`visible: foldBody.visible`，设置折叠节默认收起）里。
所以断言量的其实是"折叠节开没开"，不是"警告该不该出现"。

规矩：**凡是断言折叠体/抽屉里的控件 `visible`，先 `page.setProperty("_zSetupOpen", True)`
+ pump，测完再恢复**（直接 `setProperty` 是既有手法）。要量"绑定算出来的值"就用
面板暴露出来的属性（`homeMaTooLow`），别拿被传染的 `visible` 当判据。
（`isVisible()` 也要小心：它是**有效**可见性，父项不可见时同样为 false ——
这次两者一起骗了我，因为真正要问的是"绑定条件成立吗"。）

### 35. `Layout` 的子项用 `width`/`height` 定尺寸 —— **会被布局覆盖**（2026-09-29）

用户看着 Z 轴连接卡说"后面两个图标有点大"。查下来不是审美问题，是**那两个图标的尺寸
从来没生效**：`IconImage` 是 `RowLayout` 的**直接子项**，代码里写的 `width: 11; height: 11`
被布局忽略了 —— Qt Quick Layouts 会给子项**分配**几何，实际尺寸由
`implicitWidth/implicitHeight`（`IconImage` 里写死的 **24**）或 `Layout.preferred*` 决定。
所以那两个图标一直按 **24px** 画在 11px 的数字旁边。

规矩：**凡是进了 Layout 的项，尺寸一律写 `Layout.preferredWidth/Height`**（要固定大小）
或 `Layout.fillWidth` + `Layout.minimum/maximum*`（要弹性）。写 `width:`/`height:` 在布局里
等于没写 —— 而且**不报错、不打警告**，只有量出来才发现（这次就是测试断言 `width == 9`
读出 `24.0` 才抓到的）。

同类扫描一次发现 5 处（都在 `RowLayout` 里）：
`StageControllerCard` 的电压/信号图标（原写 11，实际 24）、
`StageJogPanel`/`ZStageJogPanel` 的卡标题图标（原写 16）与「绝对定位」的靶心（原写 13）。
**用 `anchors.centerIn` 放在 `Rectangle` 里**的那些（各页卡片的 48px 图标 chip）不受影响 ——
它们不在布局里，所以 `width: 32/40` 是有效的。这条区别要记住：
「在布局里」和「在 Item/Rectangle 里锚定」是两种写法。

⚠⚠ **第二个坑紧接着来了（同一天）**：只把它们改小（`Layout.preferred 9`）之后，
用户反馈**"图标直接消失了"**。两个原因叠在一起，最后是靠这三条一起才稳：

1. `IconImage` 的染色走 `ColorOverlay`（`ShaderEffectSource`）：**创建之后被布局改尺寸**
   可能拿不到（或拿到过期的）纹理 → 什么都不画。所以**尺寸必须在创建时就定死**：
   同时写 `implicitWidth/implicitHeight` 和 `Layout.preferredWidth/Height`（同一个值），
   布局那一趟只是把它"确认"成同样的尺寸，不产生变化。
2. 我当时还顺手把颜色从 `Colors.iconColor`(深色) 改成了 `textPlaceholder`(浅灰) ——
   **9px 的浅灰在浅色卡片上几乎看不见**。全站的语言本来就是"**图标深、标签灰**"，
   改它属于画蛇添足，已改回默认 `iconColor`。
3. 大小取 **10px**（比 24 小一大截，又比 9 好认）。

⚠ 探针脚本在这个问题上**给不出结论**：离屏渲染下 `Layout.preferred 9`、`implicit 9`、
`anchored 9`、`24` 四种写法**全都画得出来**（连"消失"都复现不了）——
又一次验证 §32 那条：探针能证"能"，不能证"不能"。这种问题只能靠
① 用户真机反馈 + ② 把决定写进测试断言（尺寸 + implicit 尺寸）来钉住。

⚠ 断言尺寸时注意：**布局只给"可见"子项分配几何**。不可见的图标会保持
`implicitWidth`(24)，那是正常现象 —— 测试里要么只对可见项断言，要么断言
`Layout.preferred*` 本身，别把这个当成回归（这次的测试第一版就误报了 2 条）。

## 五、参数与数据一致性

### 4. 跨层参数范围必须"以固件为准"，且用户要能看到实际下发的指令

`StageBridge` 原来把 `acc` 夹到 **255**、滑块也放到 255，而固件 `pd42s1.c::cmd_move` 是
`if (speed_rpm > 6000 || acc > 200) return -1;` —— **201~255 这一段会被固件静默拒帧**，
用户表现是"改了加减速没反应"。现已对齐为 `MAX_RPM=6000 / MAX_ACC=200`。

配套两条，缺一条用户就会继续怀疑参数坏了：

- **参数改动要立即生效**：`SliderRow` 的 `onReleased` 直接 `StageBridge.setSpeed(...)`，
  不必等「应用设置」。（拖动时期待的就是立刻生效。）
- **日志里记下实际下发的原始指令**：`StageBridge._enqueue` 对**非轮询命令**打 `→ <cmd>`，
  所以诊断面板能看到 `move 2250.000 0.000 120 50` —— 末尾两个数就是 rpm/acc。
  这是"我调了速度到底生效没有"最直接的证据，也是这次排查的抓手。
- ⚠ 还要**主动说明"为什么看不出来"**：步进点动 0.1~10mm 只有几十毫秒，
  基本被加减速斜坡吃掉，**怎么试都看不出速度差别**。界面已写明，并给出参考时长
  （走 100mm 约几秒）与"要验证请用长距离绝对移动"。

### 5. 新增「采集所有权」的持有者时，有三处必须同时改

相机只有一台，跨页互斥靠 `AppBridge.collectingOwner`（取值见 main.py 的
**`COLLECTING_OWNERS`**）。新增一个持有者要同时改：

1. `main.py` 的 `COLLECTING_OWNERS` 元组（setter 的合法性校验）
2. `main.py` 的 `_on_collecting_owner_changed` 里的仲裁分支（真正启停采集）
3. 页面自己（申请 / 释放 / 离开时释放）

⚠ 踩过的坑：加平台页实时预览时**只改了第 2 处**，漏了元组 →
`collectingOwner = "stage"` 被 setter **静默丢弃** → 开关点下去自己弹回来、
什么也不发生，而且没有一行日志。用户原话是"实时预览那个按钮没有作用"。

现在两道防线：
- setter 遇到未知 owner 会**明确打印警告**（不再静默）。
- `tests/test_stage_page.py` 的 `check_collecting_owners()` 做**静态校验**：
  页面里写到的每个 owner 都必须在 `COLLECTING_OWNERS` 里，并且都有仲裁分支；
  反过来声明了却没人用也会报错。（已验证：把 "stage" 从元组里拿掉，测试立刻失败。）

现有的四个取值：`""`（无人持有）/ `"collect"`（图像采集页）/ `"detect"`（异常检测页）/
`"stage"`（平台页的实时预览，只取画面、不推理不存盘）。
抢占策略是**后按者抢占**，先按者的页面靠派生属性自动显示为"已停止"；
每个页面都必须在**离开时释放**（StackLayout 里页面不会被销毁）。

### 7. 错误提示要分"粘性/非粘性"，否则要么甩不掉要么看不见

`StageBridge._set_error(msg, sticky=)`：
- **粘性**（默认）＝要用户处理：参数没填、缺基准、固件 `#ERR` 拒绝。**不能自动清**，
  否则用户来不及看见原因。
- **非粘性**＝传输类：超时、socket 错误、连接断开。**必须在链路恢复后自动消失**
  （命令成功时 `_clear_if_transient()`）。

原来只有一种错误、且只在"重新连接"时清空，于是**一次超时之后诊断面板一直挂着
"超时（板子没有应答）"**，哪怕板子早就好端端在应答了 —— 用户原话是"不会自己消失"。

### 19. 量程/上限这类"跨层事实"，只许有一份

2026-09-13 用户问"速度能不能到 3000rpm"，查下去发现一个典型坑：

`stage_bridge.py` 里**已经声明**了 `UI_MAX_RPM = 1200`，还带着注释解释为什么是 1200 ——
**但从来没有任何地方引用它**。滑块里是硬编码的 `to: 1200`。
于是"改常量"对界面**完全无效**，而两边看起来都很正常。

**修法**：bridge 暴露 `uiMaxRpm` / `uiMaxAcc` 两个 Property 当**唯一事实源**，
QML 写 `to: StageBridge.uiMaxRpm`；并加回归守卫
（`test_stage_page.py` **11c6**）断言 `滑块.to == StageBridge.uiMaxRpm`
**且** `uiMaxRpm <= 固件上限 6000` —— 界面**不能**给出固件会拒收的值（那等于"拖了没反应"）。

**通用判据**：一个数字如果同时出现在"后端常量"和"前端控件"两处，
那它**迟早会漂移**；而且漂移的表现是**静默的**（只是范围小了一点，没人报错）。
凡是这种数字，都要么从前端读后端，要么有一条断言把两边钉在一起。

顺带把手册查清楚了：**驱动器最高 6000 RPM**（不是 3000，也不是我们原来以为的 1200），
`0xF3` 的速度字段也是 `0~6000`。界面给 3000 是"扭矩还能带点载"的实用顶 ——
"驱动器能输出"和"电机带得动"是两件事（1.8° 电机 3000rpm = 10kHz 电频率，24V 下扭矩掉得快）。

### 22. "改动就生效"的参数：量程/上限只许有一份

Z 轴的速度/加减速滑块量程来自 `ZStageBridge.uiMaxRpm/uiMaxAcc`（= 固件上限），
界面**不许硬编码**。同一个数字出现在"后端常量"和"前端控件"两处，迟早漂移，
而且漂移是静默的（只是范围小了一点，没人报错）—— 同第 19 条。
回归守卫：`test_zstage_page.py` 断言 `SliderRow.to == ZStageBridge.uiMaxRpm`。

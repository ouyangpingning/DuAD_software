# 17 二轴平台与 WiFi 控制

> 目标：在异常检测上位机中新增「平台控制」页，通过 **WiFi** 远程控制 CoreXY 二轴平台的相机位置。
> 板子固件仓库：`研究生毕业设计/esp/Steppermotor`（其 `AGENTS.md` 是硬件与协议的事实源）。

## 1 目标与边界

**要做的**：把相机移到指定位置。完整动线 = *连接 → 立基准 → 移动到目标 → 看画面确认*。

**不做的**（避免范围蔓延）：
- 不做第二个「异常检测」页：预览只是定位用的，全功能图像页仍是 `DetectPage`。
- 不做平滑连续点动（见 §5.3，链路带宽决定了做不出手感）。
- 不做 TLS/加密：局域网内用口令 + 单客户端限制即可（论文演示场景）。

## 2 为什么 WiFi 不是「加个页面」的事

ESP32 侧当前**完全没有网络栈**，这是本项工作的主要成本：

| 检查项 | 现状 | 影响 |
|---|---|---|
| `sdkconfig` | 只有 `CONFIG_SOC_WIFI_SUPPORTED`（芯片能力标志），无 lwip / esp_netif / esp_wifi | 必须动 menuconfig 开栈 |
| flash / 分区 | 2MB flash，默认 `partitions_singleapp` → **factory 仅 1MB**，原 app 252KB | WiFi+mbedtls 实测 **+567KB**（→819KB）、加 TCP/json 后 **834KB**。默认 1MB **装得下**（余 205KB），但余量太薄 → 已改成 factory 1.94MB（余 1.19MB） |
| 根证书 bundle | `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_DEFAULT_FULL=y`（200 张） | 不上 TLS 就关掉省 flash（已关） |
| `console_cmds.c` | 1150+ 行 / 29 条命令 / **90 处直接 `printf`** | 输出没有去处抽象，TCP 无法复用命令 → 先做 sink 解耦（已完成，改名 `out(...)`） |
| `wait_done` | 纯阻塞循环，无 abort 检查 | `g0` 阻塞数秒 → **急停会被排在长移动后面**（见 §5.2）。已用非阻塞 `move` 规避，不必改 `wait_done` |
| 模块天线 | `ESP32-WROOM-32UE` = **外置天线版**（IPEX/U.FL，无板载 PCB 天线） | 不插天线 WiFi 只有几厘米距离，**先确认天线已插** |
| 任务配置 | `FREERTOS_HZ=100`、`MAIN_TASK_STACK=3584` | TCP 任务自开栈；⚠ 网络轮询会重演 `pdMS_TO_TICKS(5)==0` 忙等饿死 IDLE 的坑 |

> ✅ 网络层**不依赖皮带修复**：`ver all` / `stat all` / `pos all` / `lim` 都不动电机，足以打通整条链路。

## 3 架构

```
StagePage.qml ──(属性/信号/槽)── StageBridge (PySide6 QObject)
                                    │  QTcpSocket（QtNetwork，异步，走事件循环）
                                    ▼
                              WiFi (STA, 实验室路由器/手机热点)
                                    ▼
                     ESP32: TCP server (单客户端 + 口令)
                                    │  行分隔 UTF-8 文本，命令语法 = USB 控制台
                                    ▼
                        console 命令层（USB REPL 与 TCP 共用同一套命令 + 同一套安全闸）
                                    ▼
                        motor_bus ─ UART1/UART2 ─ PD42S1 ─ 电机
```

**为什么不用 MQTT**：项目里已有 `MqttBridge`，但点动控制经 broker 多一跳、现场还要养一个 broker，且连接状态不如 socket 干脆。TCP 直连的「连上/断开」是即时事件，正适合做安全判定。

**为什么 TCP 复用文本命令而不是自定义二进制协议**：
1. 23 条命令 + 三道安全闸 + 全部诊断输出**零成本复用**，且 `docs/使用说明.md` 直接适用。
2. USB 控制台和 WiFi 行为完全一致 —— 不会出现「两条路径语义不同」这种最难查的 bug。
3. 调试时 `nc <ip> <port>` 就能手工敲命令，与现场排障方式一致。

## 4 通信协议

### 4.1 传输
- ESP32 做 **TCP server**（上位机主动连），端口自定义（建议 `3333`）。
- **单客户端**：已有连接时拒绝新连接（避免两个控制源同时动电机）。
- **口令**：连接后第一行必须是口令，错误则立即断开。口令存 NVS，开机在 USB 控制台打印一次。
- 分帧：`\n` 结尾的 UTF-8 文本行；应答也以 `\n` 结尾。

### 4.2 命令：直接复用 REPL 命令集
`ver` / `stat` / `pos` / `zero` / `g0` / `stop` / `en` / `dis` / `travel` / `cur` / `curset` / `mode` / `lim` / `err` …

### 4.3 新增 `json` 遥测命令（性价比最高的一条固件改动）
一次返回 UI 需要的全部量，避免轮询 4 条命令再解析人眼可读文本：

```json
{"x":123.4,"y":-45.6,"v":24.2,"en":1,"datum":1,"moving":0,"rssi":-58,"err":""}
```

| 字段 | 含义 | 来源 |
|---|---|---|
| `x` / `y` | 台面坐标 mm | `pos`（A/B counts）经 CoreXY 逆解 + mm 换算 |
| `v` | 母线电压 V | 0x24 |
| `en` | 是否使能 | 0x2F |
| `datum` | 是否已立基准 | `s_datum` |
| `moving` | 是否在运动中 | 新状态位 |
| `rssi` | WiFi 信号 dBm | `esp_wifi_sta_get_ap_info` |
| `err` | 最近一次错误摘要 | 新状态位 |

**轮询频率**：空闲 1Hz、运动中 5~10Hz。位置读是驱动器事务（每轴约 10 余字节 + ≥2.5ms 间隔），10Hz 双轴余量充足；瓶颈在 WiFi 往返。

### 4.4 `g0` 必须能非阻塞
现状：`g0` 一路等到位才返回，长行程数秒。后果是**急停要排队**。
改为 `g0` 立即返回，由上位机轮询 `json` 的 `moving` 判到位 —— 顺带得到运动中实时位置与进度条。

### 4.5 `stop` 必须能抢占
`wait_done` 循环里加 abort 标志，TCP 任务收到停止类命令时**直接置位**（不再排入命令队列）。这是安全底线，不是优化项。

## 5 点动方式与手感

### 5.1 步进式点动（本方案）
每次按键 = 一个**明确目标**的相对移动（`g0` 增量），步长可选 `0.1 / 1 / 10 / 50 mm`。
优点：与现有命令集和安全闸 100% 兼容；丢包最多多走一格，天然安全；无需看门狗。

### 5.2 按住连发
固定间隔（约 150ms）连发下一格，**队列深度 1**：上一格未到位不发下一格。收到断开事件立即停止连发。
因为每格都有明确目标，即使链路中断，最坏结果也只是多走完当前这一格。

### 5.3 为什么不做「按住平滑连续走」
单次往返 = WiFi 往返 + 板子串口（每帧 ≥2.5ms 间隔）+ 驱动器应答 ≈ **20~60ms**。
**速度上限卡在链路而不是电机**，靠上位机连发小增量做不出平滑手感。
若二期确实要平滑：必须在**固件**里加「速度模式指令 + 300ms 无指令自动停」的看门狗，而不是在上位机连发。

## 6 坐标系与单位

- **台面坐标系**：`+X = 右`，`+Y = 向里`（台面是水平面）。页面上要有轴向示意图，不能让人猜。
- **图像坐标系开关**：相机图像 Y 通常朝下，提供「跟随图像坐标系」开关，让界面数字与预览中看到的方向一致，避免每次心算翻转。
- **单位一律用 mm**：皮带轮 GT2-16T → 每圈 32mm → **1600 counts/mm**（`1mm = 11.25°`）。
  ⚠ 固件 `travel`/`g0` 目前参数域是**度** —— 要么 `StageBridge` 换算，要么先把固件换算改成 mm（`Steppermotor/AGENTS.md` 第 7 步）。**不要两边混用。**
- ⚠ **UI 只暴露 `g0`，绝不暴露 `turn`**：`turn` 是单电机相对转动 = 45° 斜线，对相机定位毫无意义。

### 7.2 详略分层
原则：**主线「把相机移到某个位置」必须在首屏一眼走完**；凡是"让电机转起来"的底层参数全部往下压。

| 层级 | 内容 | 理由 |
|---|---|---|
| **首屏必显** | 连接状态 + IP；X/Y 实时坐标；步长；十字方向键；**停止**；**回零**；绝对定位输入；预设位置列表 | 每次用都要碰 |
| **常驻但小** | 状态条：电压 / 使能 / 是否已立基准 / 行程 / 信号强度 | 「现在能不能安全地动它」一眼可见 |
| **折叠（默认收起）** | 速度与加减速；网络参数（IP/端口/口令）；工作区（行程）设置；电流（`curset`）；回零参数（`hset` 方式/方向/限速/限位电流）；驱动细分/模式 | 调一次就不动 |
| **不在本页** | 协议细节、`raw`、A/B 电机角度 → 仅"诊断"内只读小字 | 调试信息，不是操作 |

### 7.3 必须具备的交互细节
1. **工作区缩略图**：方块 + 当前点 + 目标叉。空间感远强于两个数字，且能直观看到"快到边界"。
2. **轴向示意图**：直接画出 `+X = 右`、`+Y = 向里`。
3. **禁用必须说明原因**：基准未立 / 行程未设 / 未连接时，按钮变灰的**同时**在旁边写一行原因 + 就地一个 `[回零]`。
   这直接对应固件四道闸（基准闸 `s_datum`、行程闸 `s_travel`、50 圈防呆闸 `PD42S1_MAX_MOVE_COUNTS`、运动互斥闸 `s_motion_lock`）——不暴露拒绝理由，用户只会看到"点了没反应"。
   其中「运动互斥闸」会让并发运动互相拒绝（`已有运动指令在执行`），UI 要把它当成"稍后重试"而不是错误。
4. **目标先夹取再发**：UI 按工作区矩形夹住目标并显示夹取后的值，固件那道闸只当兜底。
5. ⚠ **预设位置的生命周期**：驱动器是**单圈编码器，掉电丢多圈位置**（手册 2.3③）。预设只在"本次上电回零之后"有效，页面上必须标出 —— 否则重新上电后「前往预设②」会走到一个完全错误的位置还理直气壮。

## 8 StageBridge 设计

`QObject` + `@Slot`/`Property`/`Signal`，在 `main.py` 里 `setContextProperty("StageBridge", …)` 并**加入 keepalive 列表**（context property 不增加 Python 引用计数，被 GC 后 QML 侧变 `null` → "点了没反应"）。

- **`QTcpSocket`**：异步、走 Qt 事件循环，**不要**用 `LightBridge` 那种线程 + 阻塞读。
- **分帧**：`canReadLine()` + `readLine()`；应答按行分发。
- **请求/应答关联**：单在途请求 + 超时（长移动的超时必须大于固件的 `wait_done` 上限）。
- **轮询**：空闲 1Hz / 运动中 5~10Hz 发 `json`，驱动全部状态属性。
- **指令队列深度 1**：运动中不接受新的点动，但 **`stop` 永远立即发**（走抢占路径）。
- **断线处理**：`disconnected` → 停止连发、清空队列、UI 进入"未连接"，所有运动控件禁用。
- **`collectingOwner` 加第三个 owner `"stage"`**：预览要拿帧就得走 `startGather`，而采集由 `main.py` 的 owner 仲裁（现仅 `"collect"`/`"detect"`）。不加的话会和 `DetectPage` 抢相机。离开页面时释放 owner。

## 10 坑（易踩）

1. **`.ui.qml` 三处同步**：`NavButton` / `ButtonGroup.buttons` / `StackLayout` 顺序，漏一处则整组页面错位。
2. **桥必须 keepalive**，否则 QML 侧静默失效。
3. **颜色禁止硬编码**，一律 `Colors.xxx`（有状态单例，主题/配色切换靠它做渐变）。
4. **相对 URL 按所在 qml 文件解析**：`pages/` 引 `images/` 要写 `../images/`。
5. **`pdMS_TO_TICKS` 在 100Hz 下取小值会得 0** → `vTaskDelay(0)` 不阻塞 → 忙等饿死 IDLE → task WDT 刷屏。网络轮询/超时循环都必须保证至少睡 1 tick。
6. **`g0` 的阻塞语义**：不加非阻塞开关，急停就形同虚设。
7. **单位混用（度 vs mm）**是最容易埋进去的静默错误 —— 界面全 mm，边界处只换算一次。

## 11 实施中发现的新限制（写下来免得以后再踩）

1. ~~**网络回零会占满整个通道**~~ —— ✅ **2026-09-13 真机踩到后当天修完了。**
   原现象（用户原话）：**"滑块撞到边缘后不会停止……然后在上位机按停止没反应。"**
   根因两条，缺一不可：
   - **固件侧**：TCP 任务串行，阻塞版 `home` 要等到回零结束才回话，`stop` 只能排在它后面；
   - **驱动器侧**：电源被限流到 400mA，顶住时驱动器欠压 → 回零永远结束不了，
     于是那条阻塞的 `home` 也就永远不返回。

   固件新增 `home ... nowait`（立即返回，状态走 `json` 的 `"homing"` 字段）、
   `stop` 兼作回零急停（自动补 0x93）、超时兜底自动 0x93。
   上位机侧 `homeAll()` 改用 `nowait`，并新增「中断回零」按钮与回零状态行。
   **教训**：一条"点了没反应"的报障，可能是**两层**原因叠在一起 ——
   先查通道，再查负载，不要只修其中一层就宣布解决。
2. **`SwitchRow` 的 `on` 被内部 `on = !on` 改写，会打断外部绑定**。
   预览开关的状态来自 `AppBridge.collectingOwner`（会被外部改：离开页面释放、被 Detect 抢占），
   所以必须用 `Connections` 显式回同步，否则回来会看到"开关是开的、画面却没有"。
3. **写测试替身时漏属性会伪装成页面 bug**。假 `AppBridge` 少了 `cameraConnected`，
   页面立刻报 `Unable to assign [undefined] to bool` —— 看着像页面写错了属性。
   教训：替身要按"页面实际引用的每一个属性"逐个补齐。
4. **offscreen 下那些 `TypeError: Cannot read property 'xxx' of null` 是退出时的噪音**，
   不是加载期错误 —— 它们在 Python 侧对象先于 QML 对象被回收时产生。
   判断"到底是不是真错"要看**加载完成后那一刻**的 `engine.warnings`，不要看进程末尾的 stderr。
5. **验证"步长生效"要用实际幅度**（发一次点动，看板子收到的角度对不对），
   只断言 `step == 10` 只能证明赋值成功、证明不了它被用上了。
6. **假板子对"慢命令"的建模会掩盖真实缺陷**。原来的 `FakeBoard.handle("home")` 是
   `time.sleep(0.3)` 后返回 —— 于是"阻塞 `home` 期间 stop 进不来"这条在测试里**根本复现不出来**。
   现在替身按固件真实语义实现：带 `nowait` 才立刻返回，不带就睡；`stop` 会顺手把
   `homing` 置成 3。**替身的不诚实，会让测试给出虚假的安全感。**
7. **限流电源的表现具有欺骗性**：`400mA 不涨` 看着像"电流环在正常工作"，
   实际是电源进了恒流模式。判断必须看**母线电压**（`json` 的 `v` 字段 / `stat`），
   不是看电流。这一条同时写进了固件 `AGENTS.md` 与《使用说明》§6.5。

## 11.1 「点连接就回零」：**连接序列本身把电机动了**（2026-09-13）

用户原话：**"这个自动回零会在上位机点击连接的时候回零，其他情况不会回零。"**

排查（值得当成一个模板）：把"连上之后到底发了什么"逐条列出来 ——
`_on_ready_read` 里只有 **`travel` + 两条 `hset`**（外加启动 `json` 轮询）。
`travel` 是纯固件闸（不碰总线）、`json` 只读 → **唯一碰总线的是 `hset`**。
固件的 `travel`/`hcfg` 也都确认不动电机。于是结论只能是：
**驱动器收到 0x91 之后自己开始找零点了**（手册没写，但这台 fw V1.7 就是这样）。

**改法（上位机侧）**：
- 新增固件命令 `hcfg`（只写板子 RAM）：`_send_home_cfg()` 改用它 —— 
  **连接时的自动重下发从此不可能动电机**。
- 「应用回零参数」也走 `hcfg`。
- 回归守卫：`tests/test_stage_bridge.py` **14f4** 断言连接后的命令序列里
  没有任何 `hset/home/move/g0/turn/abs/zero`。

**教训**：**"连接"不是一个无害动作。** 任何在连接时自动下发的命令，
都要先问一句"对端收到它会不会动"。以前那行 `if self._home_cfg_saved: self._send_home_cfg()`
的注释写着"因为固件的 hset 只存 RAM"，那是**固件侧**的理由 —— 但代价发生在驱动器侧。

## 11.2 角落回零：为什么以前到不了角落（2026-09-13）

用户原话：**"现在回零只有左右回零，没法在角落里回零，也就是没有 Y 轴里外的回零。"**

根因不在固件、也不在驱动器，而在**界面的表达力**：
原来只有一个「方向反转」开关，**两轴共用** —— 而 CoreXY 里
**两轴同向 = 纯 X、两轴反向 = 纯 Y**，所以"两轴永远同向"就永远只能做一个方向。

**改法**：把"想要哪个角"当输入，**方向由固件按 `COREXY_DEFAULT` 反推**。
- 固件新增 `corexy_dir_to_joints()`（放在 corexy 组件，主机可测）+
  `home x|y <±1>`（单趟）/ `home corner <xdir> <ydir>`（两趟，先 X 后 Y）。
- 上位机：`HOME_CORNERS`/`HOME_CORNER_NAMES` + 「目标角落」下拉 + 「角落回零（两趟）」按钮，
  外加四个**单趟**按钮（调试用：第一次到新角落前先确认方向）。
- 那个「方向反转」开关**删掉了** —— 它在新流程里完全无效，
  留着就是"点了没反应"（AGENTS.md 第 2 条）。台架要用，走控制台 `hset`。

**教训**：**界面表达不了的东西，功能就等于不存在。** 固件一直支持任意方向组合，
但界面只给了"一个方向"，用户就认为"没有 Y 轴回零"。设计参数表时要问：
"用户要描述的自由度，这个控件够不够表达？"


## 11.3 口径改了：主线是「手动立基准」，自动回零降级为可选（2026-09-13）

用户拍板原话：**"其实这个零点我可以写一次，然后一直固定的。也不必须重新回零。
无限位回零条件有点多，还得考虑平台的结构。"**

这个判断对（固件侧记录见 `Steppermotor/docs/使用说明.md` §6.3、`Steppermotor/AGENTS.md`
的「⭐ 决策」一节），而且与**固件《使用说明》§6.4 早就写的推荐用法**一致
（"用手把滑座推到机械角落，然后 `zero all` + `travel ...`，重复性由机械死点保证，
绝对精度最后再由相机拍图做闭环修正"）。上位机侧只改了**口径**，
没有改任何行为 —— 四道闸、非阻塞回零、诊断面板的能力全部保留：

| 位置 | 改前 | 改后 |
|---|---|---|
| `StagePage.qml` `_gateHint` | 「缺少基准：点『把当前位置设为原点』，或展开诊断做自动回零」 | 「缺少基准：**每次上电都要重立一次** —— 先把滑座推到靠块/硬限位贴实，再点『⌂ 把当前位置设为原点』」 |
| `StagePresetPanel.qml` 常驻警告 | 「重新上电后**必须先回零**」 | 「重新上电后**必须重新立一次基准**（推到位 → 点『设为原点』）」 |
| `StageDiagPanel.qml` 头部注释 | 只写"这里是自动回零的地方" | 补一句**自动回零是可选、不是主线**，以及主线怎么走 |
| `stage_bridge.py` `datumHint` | 「请先『设为原点』（或自动回零）」 | 「缺少基准（**每次上电都要重立**）：推到位后点『设为原点』」 |

⚠ **必须纠正的那个误解**：「零点写一次就一直固定」**做不到** —— 绝对位置模式用**单圈编码器**，
驱动器一掉电就丢多圈位置（手册 2.3③）。**能固定的是物理位置（靠块/硬限位），不是驱动器里的数。**
所以"每次上电重立基准"这一步省不掉，界面上必须一直这么说，不能给人"设一次管一辈子"的错觉。
→ 这也正是那句提示**常驻不折叠**的原因（§7.3）。

**怎么保证每次都推到同一个物理位置**（重复性由机械给，不由代码给）：
**定位销/靠块（最推荐，几十微米，对相机平台足够）** > 手推顶到硬限位 > ~~让电机自己顶~~
（那就是无限位回零，会磨皮带）。

**顺带抓到一个真 bug（i18n，与本次改动无关但同一次发现的）**：
`scripts/gen_translations.py` 的 EN 和 TW 是两个独立 dict，而生成方式是
"先用英文填 `app_en.ts`，再**整体拷贝**成 `app_zh_TW.ts`，然后用 TW dict 覆盖"。
于是**某个源文本在两个 dict 里只要有一个漏改**，繁体文件里就会留着**英文**，
而 `lrelease` 照样报 `0 unfinished`（拷贝来的英文也算"已翻译"）—— **完全静默**。
本次实例：源的「默认 100」改成「默认 1」时只改了 EN，TW 那条成了孤儿键。
→ 已加 `check_dicts()`：EN/TW 逐条对齐，不一致就 `exit 1` 并列出条目
（**已用故意删键验证过它会红**）。改文案时**两个 dict 一起改**，别再靠人眼 diff。


## 11.4 「退出时回到零点 + 位置核对」：用户提的省事方案（2026-09-13）

用户原话：**"我手动确认一次回零位置，这样零点位置就确定了……可以在每次关掉上位机的时候
自动回到零点，然后下一次开机的时候只要没有移动电机，这个位置就不会变化。"**

**这个方案成立，而且今天就能用** —— 关键在于它背后的机制（用户没明说，但正是它成立的原因）：

> **驱动器只要不断电，就一直用编码器数着位置。**

所以基准的存活条件只有两条，**跟上位机一点关系都没有**：

| 事件 | 基准还在吗 | 为什么 |
|---|---|---|
| 关上位机 / 断 WiFi / 上位机崩掉 | ✅ 在 | 固件 RAM 里的基准闸 + 驱动器编码器都没动 |
| 有人用手推台面 / 皮带打滑 | ❌ 没了 | 位置变了，而基准还指着老地方 |
| **板子 / 24V 断电** | ❌ 没了 | 单圈编码器，**一掉电多圈位置就丢**（手册 2.3③） |

→ **"退出时回零点"其实不是保住基准的手段**（不回零点基准也照样有效）。
它的真正价值是：**把台面留在一个已知姿态**，于是下次开机能用
"还在不在那个角上"来**核对"我们不在的时候有没有人动过它"**。

### ⚠ 这套方案唯一会咬人的地方：`pos == 0` 不能证明"在零点"

**驱动器上电时也是从 0 开始数的** —— 于是"随便停在哪儿"和"正好停在零点"
读出来**一模一样**。只看位置就会把"刚上电"误判成"已经回到零点"，然后放心地开出去。

**所以判据必须是两个一起**（`StageBridge._check_park`）：

```
固件的 datum == 1 ？   ← 基准闸在 RAM 里，板子一重启就清空 —— 它才是"电源有没有断过"的证人
        │
        ├─ 否 → 板子重启过 → **基准作废**，提示"推到位 → 点设为原点"
        └─ 是 → 再看位置跟"上次停在哪儿"差多少
                 ├─ ≤ 0.5mm → 没被动过，坐标可信
                 └─ > 0.5mm → 有人推过 / 皮带打滑 → 提示重立基准
```

### 实现（全在上位机，固件一行没改）

| 位置 | 内容 |
|---|---|
| `stage_bridge.py` `parkAndDisconnect()` | 退出时调：`move 0 0`（按工作区夹取）→ 等应答 → 等 `moving` 归 0 → 记下实际位置。**8s 上限，超时只记日志**，绝不拖住退出 |
| `stage/last_park_pos` | **只有"正常退出且真的停稳在零点"才写** —— 崩溃/超时那次留空，下次就不核对（宁可不查，也不报假警） |
| `stage/park_on_exit` | 设置项，默认**开**；界面在「平台设置 › 关机行为」 |
| `_check_park()` | 连上后**第一次遥测**时执行一次（位置还没到手时判不了） |
| `forgetParkPos()` | `zeroAll()` 里调 —— 刚立的基准就在脚下，旧记录没意义了，留着下次必报假警 |
| `main.py` `_shutdown()` | 调 `parkAndDisconnect()` 而不是 `disconnectDevice()` |

**为什么 `_enqueue` 那行不能写成 `if not self._enqueue(...)`**：它**没有返回值**，
`not None` 恒为真 → 会"发了就走"，真机表现是**永远不回零点**。
（`test_stage_bridge.py` 16 组用假板子把这条钉住了：断言退出时真的发了一条 `move 0.000 0.000`。）

**测试覆盖**（`tests/test_stage_bridge.py` 第 16 组，5 个小节）：
退出真的发了回零点的 move / 位置没变时**一个字都不说** / 板子重启（`datum=0` 但位置读数是 0）
必须提示重立基准 / 位置对不上要报警 / **没基准时不发 move**（免得盲开车）。

**和限位开关的关系**：两者不冲突，是"手动"和"自动"两档。
现在这套（手动立一次 + 退出回零点 + 位置核对）**够用且零硬件**；
限位开关（`seek`，见 `Steppermotor/docs/使用说明.md` §5.6）是等你想彻底免掉"手动推到位"那一步时再上。

能选就意味着可能出现"这次回左·外、下次回右·里"—— 那不是换个角落，那是**把整套坐标系挪走**，

它就是原来那个角落下拉框的可视化替代：用户一眼就知道"这个角是家"。

省掉一整行高度，而且指标和图挨着，容易对上号。
布局有测试守卫：`test_stage_page.py` **11c3** 量"缩略图 x < 读数 x"（两列并排），
组件为此暴露了 `_mapX` / `_numsX` 两个只读属性 —— **量几何，不猜**。

### 固件侧的 `home` 命令**保留**

`home`/`hcfg`/`hset`/`habort` 在固件里一个都没删（台架和 USB 控制台上还能用，
而且它们是排查"驱动器到底怎么判到位"的唯一手段）。**只是上位机不再提供入口。**
`StageBridge` 的 `homeAll()/homePass()/homeAbort()/setHomeConfig()` 也保留且**仍有测试覆盖** ——
下一步接限位开关归零时就用它们（`homeAll()` 现在已经指向写死的零点角）。

### 下一步（限位开关归零接界面）

固件已经有 `seek`（见 `Steppermotor/docs/使用说明.md` §5.6）。
⚠ **但先别急着接按钮**：`seek` 目前是**阻塞式**的（走 TCP 会把通道占住几秒），
接了就是重演"回零期间按停止没反应"。要先把它改成 `nowait` 变体
（照 `home_poll` 那套：由 `state_tick_task` 收尾、`json` 报状态），再接界面。


### 11.6 速度滑块的量程：从 1200 提到 3000（2026-09-13）

用户问：**"这里的速度可以再提高一下吗？我记得最快的速度支持 3000rpm 来着？"**

**先查手册、再改**（`pd42s1.txt` §2.1 规格页原文）：

> 最大工作电流 **3000mA**，**最高转速 6000RPM**（承载能力强），最低转速 0.1RPM

**所以 3000 不是上限，6000 才是**（`0xF3` 的速度字段也是 `0~6000 RPM`，
固件 `pd42s1.c::cmd_move` 正好卡在 6000）。**界面原来那个 1200 是我们自己设的保守值**，
不是协议限制。

**但"驱动器能输出"≠"电机带得动"**，所以没有直接开到 6000：

| 转速 | 电机圈速 | 皮带线速 | 台面（纯 X） | 360mm 行程 |
|---|---|---|---|---|
| 600 | 10 圈/s | 320 mm/s | 160 mm/s | 2.25 s |
| 1200 | 20 圈/s | 640 mm/s | 320 mm/s | 1.13 s |
| **3000** | 50 圈/s | 1600 mm/s | **800 mm/s** | **0.45 s** |

- 1.8° 电机 3000rpm = **10kHz 电频率**；24V + 4.3mH 相电感下电流来不及建立 →
  **扭矩随转速急剧下降**，3000 以上基本只适合空载。
- **加速比极速更危险**：0.45 秒内加/减到 800mm/s 对皮带和滑块是不小的冲击，
  而台面**本来就在跳齿**。更要命的是**编码器在电机轴上 → 皮带跳齿驱动器看不见**
  （它只会认为"我转到位了"），坐标会**悄悄**错掉 —— 这正是折腾了一整天的那个问题。
- 相机平台常用 **600~1200rpm**。所以：`UI_MAX_RPM = 3000`（滑块顶），
  `MAX_RPM = 6000`（固件真上限，用于夹取），两者分开记。

**顺手修掉一个"同一个事实两份"的坑**：`UI_MAX_RPM = 1200` 在 `stage_bridge.py` 里
声明得好好的，**却从来没人引用** —— 滑块里硬编码 `to: 1200`。改常量界面纹丝不动
（本项目 AGENTS 第 4 条）。现在：

- bridge 暴露 `uiMaxRpm` / `uiMaxAcc` 两个 Property（**唯一事实源**）；
- 滑块写 `to: StageBridge.uiMaxRpm`，刻度 `[60, 300, 600, 1200, 2000, uiMaxRpm]`；
- 加减速滑块同样接 `uiMaxAcc`（= `MAX_ACC` = 200，**不是 255**：固件超 200 直接拒帧）；
- 回归守卫 `tests/test_stage_page.py` **11c6**：断言 `滑块.to == StageBridge.uiMaxRpm`，
  且 `uiMaxRpm <= 6000`（界面**不能**给出固件会拒收的值 —— 那等于"拖了没反应"）。

界面上同时补了一条说明，把"扭矩随转速掉"和"跳齿看不见"两条讲清楚，
并给出**一次加一档、跑长距离看台面有没有少走**的提速方法。

### 11.7 加减速滑块改对数刻度（2026-09-13）

用户：**"这个加速度你可以再分的细一点吗？比如1-50之间可以再细分。"**

**问题**：加减速是 `0~200` 的档位，但它的"手感分辨率"是**非线性**的 ——
`1` 和 `2` 差得很远，`190` 和 `200` 分不出来。线性轨道把 1~200 平铺在一条 ~200px 的轨道上，
**1~50 只占 25% 行程**（约 50px），要拖到 `3` 得靠运气。

**改法**：给 `SliderRow` 加一个**可选的 `logScale`**（默认 false，不影响其它页面），
并把这一个滑块打开它：

| | 1~50 占轨道 | 说明 |
|---|---|---|
| 线性（原来） | 25% | 拖不准 |
| **对数（现在）** | **74%** | 一半行程就覆盖 1~15 |

配套三件事：

1. **刻度改成等比排**：`[1,2,3,4,5,7,9,12,16,21,28,37,50,67,90,120,160,200]`
   —— 每个约前一个的 1.35 倍，这样在**对数轨道上间距均匀**，刻度线不会挤成一坨。
2. **滚轮步长自适应**：`≤20 → 1 步`、`≤60 → 2`、再往上 `5`。低端才能"一格格摸"。
3. **说明文字**：讲清楚"对数刻度不是坏了"，以及**要任意整数就直接点数字输入**
   （`SliderRow` 本来就支持，只是没人知道）。

**⚠ 最关键的一步：把映射收敛到一个定义**。`SliderRow` 原来在三处各算一遍线性比例
（手柄位置 / 刻度线 x / 拖动取值），加对数后**三处都必须走同一个 `ratioOf()/valueOf()`** ——
否则手柄和刻度会对不上（而且只在低端看得出来，最难查）。已全部改走这两个函数。

**顺手修掉一个静默 bug**：`Ctrl+滚轮` 的"更细"是 `step *= 0.1`，
但 `decimals: 0` 的滑块上 `1*0.1=0.1` 再取整会**回到原值** ——
表现是"按住 Ctrl 滚轮没反应"。已改成 `step = max(step*0.1, 10^-decimals)`（保底一个显示精度）。

**回归守卫**（`test_stage_page.py` **11c7**）：断言 `logScale == true`、**`_lowShare >= 0.60`**
（量的是行程占比，不是开关本身 —— 开关是 true 而映射写错时低端照样挤在一起）、
1~50 内至少 8 个刻度、刻度上限 = 固件上限 200。

⚠ 顺带记一个测试上的坑：QML 的 JS 数组从 Python 读回来是 **`QJSValue`，不能直接迭代**
（`TypeError: not iterable`），要先 `.toVariant()`。


## 12 跨页相机冲突（预览不是"看个画面"那么简单）

「平台控制」页的实时预览要拿帧，就必须走 `CameraBridge.startGather`，
而**相机只有一台** —— 这是全项目唯一的独占资源。项目原本已有互斥机制，
预览是它的**第三个持有者**。

### 契约（三处必须同时改，见 `AGENTS.md` 第 5 条坑）

| 位置 | 作用 |
|---|---|
| `main.py` 的 `COLLECTING_OWNERS` | setter 的合法性校验（**漏了它就会被静默丢弃**） |
| `main.py` 的 `_on_collecting_owner_changed` | 真正的启停：切持有者时先 `stopGather` 再 `startGather` |
| 页面自身 | 申请 `"stage"` / 关闭时置 `""` / **离开页面必须释放** |

### 四个取值

`""` 无人持有 · `"collect"` 图像采集 · `"detect"` 异常检测 · `"stage"` 平台预览

### 行为约定

- **后按者抢占**：检测正在采集时打开预览 → 检测自动停止。被抢的页面靠
  `AppBridge.collectingOwner === "xxx"` **派生**自己的状态，所以不会出现
  "按钮显示在采集、实际早被抢走"的假活状态。
- **离开页面必须释放**：`StackLayout` 切换页面时页面**不会被销毁**（只是隐藏），
  所以 `StagePage` 在 `onVisibleChanged` 里主动释放 —— 否则相机会被一直占着，
  别的页面拿不到。
- **相机断开时统一清空**：`main.py` 的 `_on_camera_connection_changed` 会停掉所有管线
  并把 owner 置 `""`，页面上的开关会自动拨回 off。
- **采集起不来时 owner 会被退回 `""`**（例如大分辨率下 usbfs 缓冲不足，
  `ACQUISITION_START` 返回 -1010）。这会让开关"自己弹回来"，
  **所以页面必须把原因写出来**：`StagePage` 在申请后 900ms 检查一次，
  没生效就显示"预览没能启动：…"。只弹回不解释 = 用户认为按钮坏了。

## 13 回零（hset）为什么必须在界面里配

> ⚠ **2026-09-13 之后这一节要按新口径读**：自动回零已降级为**可选**（§11.3），
> 主线上位机只做一件事 —— 把滑座推到靠块后点「⌂ 把当前位置设为原点」。
> 下面讲的是**可选的自动回零**那条路，它的参数闸依然有效。
> 另外：登记参数的命令已从 `hset` 换成 **`hcfg`**（`hset` 会让这台驱动器自己开始找零点，
> §11.1），界面上的「方向反转」开关已删除（§11.2，改由「目标角落」表达）。

固件的 `home` 有一道**故意的闸**：本次会话必须先登记明确
「方式 / 方向 / 速度 / 限位电流」，否则直接拒绝 —— 因为**驱动器不回读 0x91**，
贸然触发等于用未知参数撞机械死点。

所以第一版界面只放一个「自动回零」按钮是**注定点不动**的：它会稳定地返回
`left: 拒绝 —— 本次会话还没配置过回零参数`。现在的做法：

| 位置 | 内容 |
|---|---|
| 诊断面板 | 方式（0左无限位/1右无限位/2左有限位/3右有限位）、回零速度、限位电流；**目标角落**下拉 + 角落回零（两趟）+ 四个单趟按钮 |
| `StageBridge.setHomeConfig(kind, rpm, ma)` | **分两轴各发一条 `hcfg`**（只写固件 RAM，不碰驱动器；固件不认 `all`），存 QSettings |
| 连上后自动重下发 | 固件的 `hcfg` 只存 RAM，板子重启就丢；连上后若配过就自动补发一次（**这条路径不许碰总线**，见 §11.1） |
| `homeAll()` 的前置闸 | 未配参数时**用界面自己的话说清要做什么**，而不是把固件的内部话术甩给用户 |
| 「角落回零」按钮 | `enabled: homeCfgSent` —— 没配就点不动，旁边写明原因 |

### 安全默认值（**不替用户猜方向**）

方式默认「0 左无限位」、速度 **300rpm**、限位电流 **800mA**。
方向默认 0 只是"还没配过"的占位 —— **反了会直接顶到机械死点**，
所以界面要求显式点一次「应用回零参数」，并常驻四条提醒：
电流 800~1200mA / 手放在「停止」上 / 先低速点动确认哪边是死点 / 电源限流留够 2A。

⚠ **速度别用 60rpm**（那曾是"最低档最安全"的默认值）：满行程 300mm = 9.375 电机圈
= **9.4s @60rpm**，几乎顶到驱动器默认 10s 的回零超时（还没算加减速），
**从远端起步必然"跑不到边缘就失败"** —— 真机踩过这个假故障，
所以 `_load_home_cfg` 会把存下来的 60 自动迁移成 300。
"为了安全把速度压到最低"必须**同时算一遍满行程时间 vs 驱动器超时**。

限位电流填 < 300mA 会被 `setHomeConfig` 直接拒绝：无限位回零靠它判定死点，
太小就是"推不实、永远检测不到、一直顶到超时"（实测 200mA 两轴都失败、300mA 通过）。

⚠ 仍然存在的限制：回零期间固件通道被占满，`habort` 排不进去（见 §11 第 1 条）。
